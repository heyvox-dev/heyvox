Purpose: Today `pip install heyvox` works on Apple Silicon Macs that already have a Python 3.12 toolchain. But many target users (developers using AI coding agents) don't think "pip" first — they think "brew". The Homebrew formula gives a one-command install that bundles `portaudio` (the C system dep PyAudio needs) and pins Python 3.12 via `python@3.12`, so the user doesn't have to think about any of that.   resource "openwakeword" do
    url "https://files.pythonhosted.org/packages/source/o/openwakeword/..."
    sha256 "..."
  end
  # ... more resource blocks for: pyaudio, numpy, PyYAML, pydantic, platformdirs,
  #     sherpa-onnx, pyobjc-framework-Cocoa, pyobjc-framework-Quartz, mcp, psutil,
  #     rich + their transitive deps (pydantic-core, annotated-types, etc.)

    virtualenv_install_with_resources
  end

    ```markdown
    # HeyVox Release Runbook

    This is the maintainer-only checklist for shipping a new HeyVox version. Aimed at solo-maintainer
    workflow; no team coordination needed.

    ## Prerequisites (one-time, per maintainer machine)

    - `gh` CLI authenticated against an account with `heyvox-dev` org write access
    - `python -m build` working in a clean venv (`pip install build`)
    - `brew` available for the Homebrew tap workflow
    - PyPI pending publisher already registered for the `heyvox` project (Phase 14-01 Task 0)
    - Local clone of the tap repo: `git clone git@github.com:heyvox-dev/homebrew-heyvox`

    ## Release sequence (per version)

    Order matters. The wake-word asset MUST be uploaded BEFORE the git tag triggers
    `publish.yml`, otherwise fresh-install users get a 404 on `heyvox setup`.

    ### 1. Train + ship-gate the wake-word model (if model changed)

    Skip if the model didn't change since last release.

    ```bash
    # In Google Colab — run training/hey_vox_colab.ipynb end-to-end, download hey_vox.onnx
    # Locally:
    python training/evaluate_model.py \
        --model ~/Downloads/hey_vox.onnx \
        --positives ~/heyvox-eval/test/real_voice \
        --negatives ~/heyvox-eval/test/fp_corpus \
        --sweep
    # Must exit 0 (gate PASS). Record the recommended threshold.

    NEW_SHA=$(shasum -a 256 ~/Downloads/hey_vox.onnx | cut -d' ' -f1)
    echo "$NEW_SHA"  # update HEY_VOX_MODEL_SHA256 in heyvox/constants.py with this
    ```

    ### 2. Upload hey_vox.onnx as the next release's GH Releases asset

    Critical ordering — this comes BEFORE the tag push (Pitfall 6 from Phase 14 research).

    ```bash
    NEXT_VERSION=v1.0.X  # use the version you're about to tag
    gh release create "$NEXT_VERSION" ~/Downloads/hey_vox.onnx \
        --repo heyvox-dev/heyvox \
        --title "$NEXT_VERSION" \
        --draft   # keep draft; we publish it after the tag-push succeeds
    # OR if release already exists:
    gh release upload "$NEXT_VERSION" ~/Downloads/hey_vox.onnx --clobber
    ```

    ### 3. Bump constants and version in this repo

    ```bash
    # Update heyvox/constants.py:
    #   HEY_VOX_MODEL_URL = "https://github.com/heyvox-dev/heyvox/releases/download/v1.0.X/hey_vox.onnx"
    #   HEY_VOX_MODEL_SHA256 = "<the $NEW_SHA from Step 1>"
    #
    # Update pyproject.toml [project].version = "1.0.X"
    #
    # heyvox/__init__.py auto-reads from importlib.metadata (Plan 14-01) — no edit needed.

    git add heyvox/constants.py pyproject.toml
    git commit -m "release: v1.0.X — bump constants + version"
    git push origin main
    ```

    ### 4. Tag and push — triggers PyPI publish.yml

    ```bash
    git tag v1.0.X
    git push origin v1.0.X
    # Watch:
    gh workflow view publish --repo heyvox-dev/heyvox --web
    # Should complete in ~3 min. Verify on PyPI:
    pip install heyvox==1.0.X  # in a fresh venv to smoke-test
    ```

    ### 5. Publish the GH Release (un-draft from Step 2)

    ```bash
    gh release edit v1.0.X --draft=false --repo heyvox-dev/heyvox
    ```
