# HeyVox Defect Log

## DEF-163 — Keepalive PA context freezes silently: cues stop playing, no auto-recovery

- **Date**: 2026-06-29
- **Category**: state-pollution / platform
- **Severity**: S2 (cues completely silent; voice input still works)
- **Symptom**: "listening" and "ok" audio cues stop playing. afplay fallback also silent because G535 Lightspeed parks the output path after a short silence (DEF-150 original problem). User notices only after several minutes.
- **Root cause**: OutputKeepAlive._open_stream() drops and recreates the PortAudio context on every failure (DEF-153 fix). But if the USB device flaps and the PA context stays stale indefinitely, _open_fail reaches 228+ with only a log line at attempt 24. No auto-recovery: the log says "daemon restart required" but nothing actually triggers one.
- **Fix**: Added `stale = threading.Event()` to OutputKeepAlive, set after 24 consecutive failures. Main-loop watchdog (runs every ~10s) checks `keepalive.stale.is_set()` and triggers `os.execv()` restart with a HUD banner, matching the memory-watchdog pattern.
- **Found by**: User noticed missing cues. Log showed `[keepalive] could not open silent stream (attempt 228...)`.
- **Would have caught earlier**: A metric/alert on `_open_fails >= 24` rather than a log-only message. Auto-restart at that threshold (what we're now adding) prevents the silent degradation from ever reaching 228+.

## DEF-164 — preload_model() no-op leaves a stale idle-unload timer armed, evicting a warm model mid-recording

- **Date**: 2026-07-02
- **Category**: race / timing
- **Severity**: S3 (STT still works, but pays a full un-hidden cold-reload — several seconds — right when the user is waiting for a response)
- **Symptom**: User reported "transcription is slow again, it used to be much faster." `heyvox log-health` showed STT p50=1.08s (fine) but p99=10.29s with a fat tail. Two of four cold loads (`stt_warm=false`) that day had no plausible explanation as genuine >5min-idle cold starts — one followed a 12.96s recording, the other a 53.92s recording, both far longer than the model's own load time.
- **Root cause**: `preload_model()` (`heyvox/audio/stt.py`) is correctly called at the start of every recording to hide model-load latency behind speaking time, but its already-loaded fast path was a bare `if _mlx_loaded.is_set(): return` — it never touched `_mlx_last_use` or rescheduled the idle-unload `threading.Timer`. That timer was armed 300s (`unload_secs`) after the *previous* transcription finished, independent of the new recording. If the new recording ran long enough to cross that pre-existing deadline, `_unload_mlx_model()` fired mid-recording (`_mlx_transcribing` is False until `transcribe_audio()` actually runs, so its guard doesn't block this), evicting a model that was warm and in active use. Confirmed via exact log lines in `/tmp/heyvox.log.1`: `[16:57:53] MLX model loaded in 4.9s` → `[17:02:58] MLX model unloaded after 300s idle` → `[17:03:04] TRIGGER / Stopping recording` (a NEW recording that had started ~17:02:49, 6s before the stale timer fired) → forced fresh reload with zero head start.
- **Fix**: `preload_model()`'s already-loaded branch now refreshes `_mlx_last_use = time.time()` and calls `_schedule_unload()` under `_mlx_lock`, the same way the end of `transcribe_audio()` already does — treating "a new recording started" as a use-signal, not just "a transcription completed." Commit touches `heyvox/audio/stt.py` (behavior) and `heyvox/recording.py` (stale "~1s" comment corrected to match the current model's actual load time).
- **Found by**: User asked "shouldn't reload hide behind recording start, so mostly unnoticeable?" while reviewing the STT-latency investigation — verifying that claim against the two actual cold-load log entries surfaced the timer race.
- **Would have caught earlier**: No test coverage existed for `preload_model()` / the idle-unload timer interaction at all (`grep -rl preload_model tests/` was empty before this fix). Added `test_def164_preload_model_refreshes_idle_timer_when_already_loaded` + a not-loaded counterpart to `tests/test_defect_guards.py`. General pattern: any module-level timer/last-use pair needs a test asserting *every* code path that "uses" the resource also refreshes it — not just the obvious one (transcription completion), but adjacent ones (preload-into-already-warm).

## DEF-165 — Unbounded NSPasteboard call freezes main loop for ~3 minutes after paste

- **Date**: 2026-07-02
- **Category**: timing / error-handling
- **Severity**: S1 (whole voice pipeline wedged; PTT event tap starved; process needed a full manual restart)
- **Symptom**: User reported HeyVox "super slow", possibly stuck processes. Log showed `WARNING: busy flag stuck for 60.0s, force-resetting (watchdog)`, but the freeze didn't actually clear — 46× `CGEventTap was disabled by macOS, re-enabled` followed over the next ~2 minutes (macOS repeatedly killing the PTT event tap because its callback thread never returned). Process was eventually killed and restarted manually; the next start logged `Previous instance died without clean shutdown (heartbeat stale by 61s)`.
- **Root cause**: `app_fast_paste()` (`heyvox/input/injection.py`) calls `_set_clipboard()` then `get_clipboard_text()` — raw PyObjC `NSPasteboard` calls — with no timeout. Every other blocking call in that function (both osascript `subprocess.run` calls) already has an explicit timeout (2s / 7s); these two didn't, because Python has no built-in way to bound a blocking native/ObjC call. When the pasteboard server briefly wedged, the calling (and only) thread blocked indefinitely — the busy-flag watchdog can reset a *flag*, but can't unstick the blocked thread producing it. Pinpointed by process-of-elimination in `recording.py` (the paste-outcome log line fires, then nothing — no verify/"Sent!"/fail line for that cycle — and the only statement between those two log points is the `app_fast_paste()` call), then confirmed directly in the rotated log (see DEF-166): `app_fast_paste: profile=Conductor ... text_len=360` is the last line before the watchdog fires; the function's own completion log (`[TIMING] app_fast_paste: OK ...`) never appears for that call.
- **Fix**: Added `_call_with_timeout()` to `heyvox/input/injection.py` — runs the AppKit call on a throwaway daemon thread and `.join(timeout=2.0)`, raising `TimeoutError` if it hasn't returned (the thread is abandoned, not killed — Python can't interrupt a native call — but a fresh thread per call means one abandoned call can't poison later ones). Applied to all 4 untimed AppKit call sites: `_set_clipboard`, `get_clipboard_text`, `_clipboard_still_ours`, `_verify_target_focused`.
- **Found by**: User reported perceived slowness (already manually restarted before root-causing). Diagnosed from `/tmp/heyvox.log` plus the rotated `/tmp/heyvox.log.1` — see DEF-166, the incident-window content was only visible in the rotated file.
- **Would have caught earlier**: A per-call timeout (this fix) converts what used to be an unbounded hang into a bounded, immediately-loggable failure the first time it happens, instead of requiring a live ~3-minute incident and post-hoc log archaeology to notice. General pattern: any blocking call inside a single-threaded event loop needs an enforced upper bound — `subprocess.run(timeout=...)` already gets this by convention in this codebase, but PyObjC/AppKit calls were assumed "fast enough" and never audited the same way.

## DEF-166 — injection.py/target.py `_log()` output silently lost after first log rotation

- **Date**: 2026-07-02
- **Category**: config / dead-code (logging split-brain)
- **Severity**: S2 (no functional impact on the app, but directly extended the DEF-165 investigation — the exact hang line was invisible for most of the effort)
- **Symptom**: `heyvox/input/injection.py`'s `_log()` (and `heyvox/input/target.py`'s `_log()`) never appeared in `/tmp/heyvox.log` — zero occurrences, ever, despite both being called on every single paste (`grep -c "app_fast_paste" /tmp/heyvox.log` → 0 across 7400+ lines spanning days of normal use).
- **Root cause**: `main.py`'s central `log()` rotates by `os.replace(_LOG_FILE, _LOG_FILE + ".1")` once the file exceeds 1MB, then reopens `_LOG_FILE` by path (a fresh `open()` naturally finds the new inode). `injection.py`/`target.py`'s `_log()` instead did `print(msg, file=sys.stderr, flush=True)`, relying on launchd's `StandardErrorPath` fd redirect — fixed to the inode that was open at process start. `os.replace()` repoints the *path*, not fds opened before the rename, so every stderr write after the first rotation silently landed in the renamed-away (orphaned) inode for the rest of the process's life, invisible from the live log. Confirmed: the "missing" lines were sitting, fully intact, in `/tmp/heyvox.log.1` (`grep -c "\[injection\]" /tmp/heyvox.log.1` → 258).
- **Fix**: Rewrote both modules' `_log()` to reopen the config-resolved path on every call (`open(path, "a")`), matching the already-established `main.py` / `heyvox/audio/media.py` (DEF-126) pattern. The path string is resolved once and cached (`_resolve_log_path()`) rather than calling `load_config()` per `_log()` call — an initial version re-resolved every call and regressed `_ax_inject_text`'s hot path from <5ms to >10ms mean, failing `test_ax_inject_text_phase12_fastpath_remains_under_5ms`.
- **Found by**: While root-causing DEF-165 — had to grep the *rotated* `.log.1` file to find the incident-window `app_fast_paste` entry line at all; it does not exist anywhere in the live file.
- **Would have caught earlier**: No user-visible symptom on its own, so nothing would have surfaced it directly — but it's the second occurrence of the same root cause first named for DEF-126 (see Patterns below). `heyvox/audio/mic.py`, `heyvox/input/ptt.py`, `heyvox/input/toast.py`, and `heyvox/adapters/conductor.py` all still use the same bare `print(file=sys.stderr)` pattern and are equally exposed after the process's first log rotation; not fixed here (out of scope for this incident) — flagged as a follow-up in Patterns.

## DEF-167 — Retroactive TrainingCollector relabelers manufactured mislabeled wake-word training data

- **Date**: 2026-07-02
- **Category**: state-pollution / error-handling
- **Severity**: S2 (does not crash the app or lose user-facing functionality, but silently degrades the wake-word model's own training data over time — every retrain compounds the mislabeling)
- **Symptom**: During a routine training-data audit this session, a resumable Whisper pass (`REFERENCE-fp_check_step0.py`, absorbed into `tools/quality_gate.py` by this same plan) was run over `fp/` (304 clips at the time) to check how many contained the actual wake word. It found 22 of 192 previously-unaudited fp-reclassified clips (11.5%) DID contain "Hey Vox" (including box/fox/vocks-style Whisper garbles of the user's real voice) — meaning `reclassify_tp_start_as_fp` had moved 22 genuine wake-word triggers into the false-positive training set. A companion pass over `fn_start`-reclassified clips found 54% contained NO wake word at all — meaning `reclassify_fn_start` had moved ordinary background-noise TN clips into the false-negative training set purely because a trigger happened to follow within a 5-second window, with zero evidence the TN clip itself contained speech.
- **Root cause**: Two methods on `TrainingCollector` (`heyvox/audio/training_collector.py`) performed RETROACTIVE, evidence-free relabeling based on temporal proximity/outcome heuristics rather than STT evidence: `reclassify_tp_start_as_fp(reason)` moved the most recent `tp_start` clip to `fp/` any time a trigger's recording aborted (no speech, empty STT, user-cancelled, or post-trim-too-short) — but "the recording aborted" does not prove "the wake word wasn't actually said" (the user could say "Hey Vox" correctly and then hesitate, get interrupted, or have the mic clip the recording for unrelated reasons). `reclassify_fn_start()` moved any `tn/` clip saved within the prior 5 seconds to `fn/` whenever a SUCCESSFUL trigger followed — but "a trigger followed a hard-negative sample" does not prove the hard-negative clip itself contained a missed wake word; it just means the user spoke again shortly after, for any reason. Both mechanisms manufacture training labels from correlation/timing instead of the transcript evidence that `classify_stop_outcome()` (the one relabeling path that stayed, `save_fn_stop`) already correctly required. Net effect: every `reclassify_*` call polluted the training set with clips whose true content contradicted their assigned label, and both pollution modes push the model toward FALSE NEGATIVES on the user's own voice (real positives got labeled fp; real hard-negatives got labeled fn, i.e. "should have fired here" on audio where no wake word was said).
- **Fix**: Deleted `reclassify_tp_start_as_fp()` and `reclassify_fn_start()` outright, along with the `_recent_tp_start`/`_recent_tn` tracking lists and the `fn_reclassify_window_secs` constructor param that existed solely to feed them, and removed all six call sites across `heyvox/recording.py` and `heyvox/main.py`. `save_fn_stop()` (evidence-based via `classify_stop_outcome()`, unchanged) remains the only automatic fn-labeling path from the live daemon. In its place, built a MANDATORY batch Whisper quality gate (`tools/quality_gate.py`, wired into `tools/collect_personal_features.py` ahead of every featurization run) that re-derives BOTH directions of evidence-based correction from the transcript itself: any positive-dir clip without the wake word is quarantined; any negative-dir clip WITH the wake word is recovered into `positives/` (short clips) or `quarantine/` (long clips, likely contains more than just the wake word) — this is the new evidence-based fn-recovery mechanism, replacing the deleted heuristic one, but gated on STT proof rather than timing correlation. Schritt-0 cleanup already moved 26 clips out of `fp/` manually before this fix landed (22 to `positives/`, 4 to `quarantine/`; manifest: `recfp_cleanup_manifest_20260702_084240.json`) — that hand-run pass is what the automated gate in this plan now performs on every collect run.
- **Found by**: This session's manual investigation, starting from a Whisper sanity pass over `fn/` + a backed-up `fp_garbled/` subset (`tools/whisper_sanity_pass.py`, pre-existing) that had never been run over the full `fp/` directory or the `fn_start`-reclassified clips specifically — extending that audit to ALL of `fp/` (not just the `fp_garbled` subtype) via the more robust `REFERENCE-fp_check_step0.py` driver surfaced the 22-clip contamination; a parallel audit of `fn_start` clips surfaced the 54% figure.
- **Would have caught earlier**: A MANDATORY Whisper gate over ALL training-data directories (this plan's Task 2/3) run automatically before every featurization, rather than an ad-hoc manual audit script that only ever covered a subset of one category (`fn/` and a backed-up `fp_garbled/` sample) and had to be manually re-scoped and re-run this session to find the gap. General pattern: any heuristic/retroactive relabeling of ALREADY-COLLECTED evidence-backed data (a saved audio clip is direct evidence; a temporal correlation is not) should never ship without either (a) requiring the same evidence standard as the mechanism it's "correcting," or (b) being paired with a permanent, mandatory audit step — not a one-off script run manually after the fact once contamination is suspected.

## Patterns & Process Gaps

- **P-log-path-split** (DEF-126, recurred as DEF-166): any module that logs independently of the central `main.py` `log()` risks silently diverging from "the log everyone tails." DEF-126 was a wrong-*path* variant (module read a different config field/default than main.py). DEF-166 is a wrong-*transport* variant (module wrote via stderr/fd instead of reopening by path), which is more dangerous because it works fine until the first rotation, then goes silent for the rest of the process's life with no error. **Action item**: any new module-level `_log()` must reopen the resolved log path per call (copy `_resolve_log_path()` from `injection.py`/`target.py`), never `print(file=sys.stderr)` — even though launchd also redirects stderr to the same path at startup, that redirect does not survive `main.py`'s rename-based rotation. `mic.py`, `ptt.py`, `toast.py`, `adapters/conductor.py` still need this fix; audit before the next release.
- **P-unbounded-native-call**: `subprocess.run(..., timeout=...)` is used consistently in this codebase, but PyObjC/AppKit calls (NSPasteboard, NSWorkspace, and likely others) were never given the same scrutiny because they're normally sub-millisecond — until the underlying system service (pasteboard server, WindowServer) itself stalls, at which point they block forever with no recourse. **Action item**: any new PyObjC call added to a single-threaded event-loop path (main.py, recording.py, injection.py, target.py) should go through `_call_with_timeout()` (`heyvox/input/injection.py`) rather than being called directly.
- **P-retroactive-labeling** (DEF-167): any training/label-correction mechanism which infers a label from OUTCOME OR TIMING rather than re-examining the underlying evidence (audio transcript, in this case) risks manufacturing exactly the class of error it claims to fix. **Action item**: any future auto-labeling code path in this training pipeline must be evidence-based (derive the label from re-inspecting the actual data, e.g. via STT) or must run through the same mandatory `tools/quality_gate.py` chokepoint before its output is trusted.
