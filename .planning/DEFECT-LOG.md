# HeyVox Defect Log

## DEF-163 — Keepalive PA context freezes silently: cues stop playing, no auto-recovery

- **Date**: 2026-06-29
- **Category**: state-pollution / platform
- **Severity**: S2 (cues completely silent; voice input still works)
- **Symptom**: "listening" and "ok" audio cues stop playing. afplay fallback also silent because G535 Lightspeed parks the output path after a short silence (DEF-150 original problem). User notices only after several minutes.
- **Root cause**: OutputKeepAlive._open_stream() drops and recreates the PortAudio context on every failure (DEF-153 fix). But if the USB device flaps and the PA context stays stale indefinitely, _open_fail reaches 228+ with only a log line at attempt 24. No auto-recovery: the log says "daemon restart required" but nothing actually triggers one.
- **Fix**: Added `stale = threading.Event()` to OutputKeepAlive, set after 24 consecutive failures. Main-loop watchdog (runs every ~10s) checks `keepalive.stale.is_set()` and triggers `os.execv()` restart with a HUD banner, matching the memory-watchdog pattern.
- **Found by**: User noticed missing cues. Log showed `[keepalive] could not open silent stream (attempt 228...)`.
- **Would have caught earlier**: A metric/alert on `_open_fails >= 24` rather than a log-only message. Auto-restart at that threshold (what we're now adding) prevents the silent degradation from ever reaching 228+.

## DEF-164 — preload_model() no-op leaves a stale idle-unload timer armed, evicting a warm model mid-recording

- **Date**: 2026-07-02
- **Category**: race / timing
- **Severity**: S3 (STT still works, but pays a full un-hidden cold-reload — several seconds — right when the user is waiting for a response)
- **Symptom**: User reported "transcription is slow again, it used to be much faster." `heyvox log-health` showed STT p50=1.08s (fine) but p99=10.29s with a fat tail. Two of four cold loads (`stt_warm=false`) that day had no plausible explanation as genuine >5min-idle cold starts — one followed a 12.96s recording, the other a 53.92s recording, both far longer than the model's own load time.
- **Root cause**: `preload_model()` (`heyvox/audio/stt.py`) is correctly called at the start of every recording to hide model-load latency behind speaking time, but its already-loaded fast path was a bare `if _mlx_loaded.is_set(): return` — it never touched `_mlx_last_use` or rescheduled the idle-unload `threading.Timer`. That timer was armed 300s (`unload_secs`) after the *previous* transcription finished, independent of the new recording. If the new recording ran long enough to cross that pre-existing deadline, `_unload_mlx_model()` fired mid-recording (`_mlx_transcribing` is False until `transcribe_audio()` actually runs, so its guard doesn't block this), evicting a model that was warm and in active use. Confirmed via exact log lines in `/tmp/heyvox.log.1`: `[16:57:53] MLX model loaded in 4.9s` → `[17:02:58] MLX model unloaded after 300s idle` → `[17:03:04] TRIGGER / Stopping recording` (a NEW recording that had started ~17:02:49, 6s before the stale timer fired) → forced fresh reload with zero head start.
- **Fix**: `preload_model()`'s already-loaded branch now refreshes `_mlx_last_use = time.time()` and calls `_schedule_unload()` under `_mlx_lock`, the same way the end of `transcribe_audio()` already does — treating "a new recording started" as a use-signal, not just "a transcription completed." Commit touches `heyvox/audio/stt.py` (behavior) and `heyvox/recording.py` (stale "~1s" comment corrected to match the current model's actual load time).
- **Found by**: User asked "shouldn't reload hide behind recording start, so mostly unnoticeable?" while reviewing the STT-latency investigation — verifying that claim against the two actual cold-load log entries surfaced the timer race.
- **Would have caught earlier**: No test coverage existed for `preload_model()` / the idle-unload timer interaction at all (`grep -rl preload_model tests/` was empty before this fix). Added `test_def164_preload_model_refreshes_idle_timer_when_already_loaded` + a not-loaded counterpart to `tests/test_defect_guards.py`. General pattern: any module-level timer/last-use pair needs a test asserting *every* code path that "uses" the resource also refreshes it — not just the obvious one (transcription completion), but adjacent ones (preload-into-already-warm).

## DEF-165 — Unbounded NSPasteboard call freezes main loop for ~3 minutes after paste

- **Date**: 2026-07-02
- **Category**: timing / error-handling
- **Severity**: S1 (whole voice pipeline wedged; PTT event tap starved; process needed a full manual restart)
- **Symptom**: User reported HeyVox "super slow", possibly stuck processes. Log showed `WARNING: busy flag stuck for 60.0s, force-resetting (watchdog)`, but the freeze didn't actually clear — 46× `CGEventTap was disabled by macOS, re-enabled` followed over the next ~2 minutes (macOS repeatedly killing the PTT event tap because its callback thread never returned). Process was eventually killed and restarted manually; the next start logged `Previous instance died without clean shutdown (heartbeat stale by 61s)`.
- **Root cause**: `app_fast_paste()` (`heyvox/input/injection.py`) calls `_set_clipboard()` then `get_clipboard_text()` — raw PyObjC `NSPasteboard` calls — with no timeout. Every other blocking call in that function (both osascript `subprocess.run` calls) already has an explicit timeout (2s / 7s); these two didn't, because Python has no built-in way to bound a blocking native/ObjC call. When the pasteboard server briefly wedged, the calling (and only) thread blocked indefinitely — the busy-flag watchdog can reset a *flag*, but can't unstick the blocked thread producing it. Pinpointed by process-of-elimination in `recording.py` (the paste-outcome log line fires, then nothing — no verify/"Sent!"/fail line for that cycle — and the only statement between those two log points is the `app_fast_paste()` call), then confirmed directly in the rotated log (see DEF-166): `app_fast_paste: profile=Conductor ... text_len=360` is the last line before the watchdog fires; the function's own completion log (`[TIMING] app_fast_paste: OK ...`) never appears for that call.
- **Fix**: Added `_call_with_timeout()` to `heyvox/input/injection.py` — runs the AppKit call on a throwaway daemon thread and `.join(timeout=2.0)`, raising `TimeoutError` if it hasn't returned (the thread is abandoned, not killed — Python can't interrupt a native call — but a fresh thread per call means one abandoned call can't poison later ones). Applied to all 4 untimed AppKit call sites: `_set_clipboard`, `get_clipboard_text`, `_clipboard_still_ours`, `_verify_target_focused`.
- **Found by**: User reported perceived slowness (already manually restarted before root-causing). Diagnosed from `/tmp/heyvox.log` plus the rotated `/tmp/heyvox.log.1` — see DEF-166, the incident-window content was only visible in the rotated file.
- **Would have caught earlier**: A per-call timeout (this fix) converts what used to be an unbounded hang into a bounded, immediately-loggable failure the first time it happens, instead of requiring a live ~3-minute incident and post-hoc log archaeology to notice. General pattern: any blocking call inside a single-threaded event loop needs an enforced upper bound — `subprocess.run(timeout=...)` already gets this by convention in this codebase, but PyObjC/AppKit calls were assumed "fast enough" and never audited the same way.

## DEF-166 — injection.py/target.py `_log()` output silently lost after first log rotation

- **Date**: 2026-07-02
- **Category**: config / dead-code (logging split-brain)
- **Severity**: S2 (no functional impact on the app, but directly extended the DEF-165 investigation — the exact hang line was invisible for most of the effort)
- **Symptom**: `heyvox/input/injection.py`'s `_log()` (and `heyvox/input/target.py`'s `_log()`) never appeared in `/tmp/heyvox.log` — zero occurrences, ever, despite both being called on every single paste (`grep -c "app_fast_paste" /tmp/heyvox.log` → 0 across 7400+ lines spanning days of normal use).
- **Root cause**: `main.py`'s central `log()` rotates by `os.replace(_LOG_FILE, _LOG_FILE + ".1")` once the file exceeds 1MB, then reopens `_LOG_FILE` by path (a fresh `open()` naturally finds the new inode). `injection.py`/`target.py`'s `_log()` instead did `print(msg, file=sys.stderr, flush=True)`, relying on launchd's `StandardErrorPath` fd redirect — fixed to the inode that was open at process start. `os.replace()` repoints the *path*, not fds opened before the rename, so every stderr write after the first rotation silently landed in the renamed-away (orphaned) inode for the rest of the process's life, invisible from the live log. Confirmed: the "missing" lines were sitting, fully intact, in `/tmp/heyvox.log.1` (`grep -c "\[injection\]" /tmp/heyvox.log.1` → 258).
- **Fix**: Rewrote both modules' `_log()` to reopen the config-resolved path on every call (`open(path, "a")`), matching the already-established `main.py` / `heyvox/audio/media.py` (DEF-126) pattern. The path string is resolved once and cached (`_resolve_log_path()`) rather than calling `load_config()` per `_log()` call — an initial version re-resolved every call and regressed `_ax_inject_text`'s hot path from <5ms to >10ms mean, failing `test_ax_inject_text_phase12_fastpath_remains_under_5ms`.
- **Found by**: While root-causing DEF-165 — had to grep the *rotated* `.log.1` file to find the incident-window `app_fast_paste` entry line at all; it does not exist anywhere in the live file.
- **Would have caught earlier**: No user-visible symptom on its own, so nothing would have surfaced it directly — but it's the second occurrence of the same root cause first named for DEF-126 (see Patterns below). `heyvox/audio/mic.py`, `heyvox/input/ptt.py`, `heyvox/input/toast.py`, and `heyvox/adapters/conductor.py` all still use the same bare `print(file=sys.stderr)` pattern and are equally exposed after the process's first log rotation; not fixed here (out of scope for this incident) — flagged as a follow-up in Patterns.

## DEF-167 — Retroactive TrainingCollector relabelers manufactured mislabeled wake-word training data

- **Date**: 2026-07-02
- **Category**: state-pollution / error-handling
- **Severity**: S2 (does not crash the app or lose user-facing functionality, but silently degrades the wake-word model's own training data over time — every retrain compounds the mislabeling)
- **Symptom**: During a routine training-data audit this session, a resumable Whisper pass (`REFERENCE-fp_check_step0.py`, absorbed into `tools/quality_gate.py` by this same plan) was run over `fp/` (304 clips at the time) to check how many contained the actual wake word. It found 22 of 192 previously-unaudited fp-reclassified clips (11.5%) DID contain "Hey Vox" (including box/fox/vocks-style Whisper garbles of the user's real voice) — meaning `reclassify_tp_start_as_fp` had moved 22 genuine wake-word triggers into the false-positive training set. A companion pass over `fn_start`-reclassified clips found 54% contained NO wake word at all — meaning `reclassify_fn_start` had moved ordinary background-noise TN clips into the false-negative training set purely because a trigger happened to follow within a 5-second window, with zero evidence the TN clip itself contained speech.
- **Root cause**: Two methods on `TrainingCollector` (`heyvox/audio/training_collector.py`) performed RETROACTIVE, evidence-free relabeling based on temporal proximity/outcome heuristics rather than STT evidence: `reclassify_tp_start_as_fp(reason)` moved the most recent `tp_start` clip to `fp/` any time a trigger's recording aborted (no speech, empty STT, user-cancelled, or post-trim-too-short) — but "the recording aborted" does not prove "the wake word wasn't actually said" (the user could say "Hey Vox" correctly and then hesitate, get interrupted, or have the mic clip the recording for unrelated reasons). `reclassify_fn_start()` moved any `tn/` clip saved within the prior 5 seconds to `fn/` whenever a SUCCESSFUL trigger followed — but "a trigger followed a hard-negative sample" does not prove the hard-negative clip itself contained a missed wake word; it just means the user spoke again shortly after, for any reason. Both mechanisms manufacture training labels from correlation/timing instead of the transcript evidence that `classify_stop_outcome()` (the one relabeling path that stayed, `save_fn_stop`) already correctly required. Net effect: every `reclassify_*` call polluted the training set with clips whose true content contradicted their assigned label, and both pollution modes push the model toward FALSE NEGATIVES on the user's own voice (real positives got labeled fp; real hard-negatives got labeled fn, i.e. "should have fired here" on audio where no wake word was said).
- **Fix**: Deleted `reclassify_tp_start_as_fp()` and `reclassify_fn_start()` outright, along with the `_recent_tp_start`/`_recent_tn` tracking lists and the `fn_reclassify_window_secs` constructor param that existed solely to feed them, and removed all six call sites across `heyvox/recording.py` and `heyvox/main.py`. `save_fn_stop()` (evidence-based via `classify_stop_outcome()`, unchanged) remains the only automatic fn-labeling path from the live daemon. In its place, built a MANDATORY batch Whisper quality gate (`tools/quality_gate.py`, wired into `tools/collect_personal_features.py` ahead of every featurization run) that re-derives BOTH directions of evidence-based correction from the transcript itself: any positive-dir clip without the wake word is quarantined; any negative-dir clip WITH the wake word is recovered into `positives/` (short clips) or `quarantine/` (long clips, likely contains more than just the wake word) — this is the new evidence-based fn-recovery mechanism, replacing the deleted heuristic one, but gated on STT proof rather than timing correlation. Schritt-0 cleanup already moved 26 clips out of `fp/` manually before this fix landed (22 to `positives/`, 4 to `quarantine/`; manifest: `recfp_cleanup_manifest_20260702_084240.json`) — that hand-run pass is what the automated gate in this plan now performs on every collect run.
- **Found by**: This session's manual investigation, starting from a Whisper sanity pass over `fn/` + a backed-up `fp_garbled/` subset (`tools/whisper_sanity_pass.py`, pre-existing) that had never been run over the full `fp/` directory or the `fn_start`-reclassified clips specifically — extending that audit to ALL of `fp/` (not just the `fp_garbled` subtype) via the more robust `REFERENCE-fp_check_step0.py` driver surfaced the 22-clip contamination; a parallel audit of `fn_start` clips surfaced the 54% figure.
- **Would have caught earlier**: A MANDATORY Whisper gate over ALL training-data directories (this plan's Task 2/3) run automatically before every featurization, rather than an ad-hoc manual audit script that only ever covered a subset of one category (`fn/` and a backed-up `fp_garbled/` sample) and had to be manually re-scoped and re-run this session to find the gap. General pattern: any heuristic/retroactive relabeling of ALREADY-COLLECTED evidence-backed data (a saved audio clip is direct evidence; a temporal correlation is not) should never ship without either (a) requiring the same evidence standard as the mechanism it's "correcting," or (b) being paired with a permanent, mandatory audit step — not a one-off script run manually after the fact once contamination is suspected.

## DEF-168 — Escape-stops-TTS silently dead under system load: CGEventTap re-enable only polled at 1Hz, not reactive

- **Date**: 2026-07-02
- **Category**: timing / platform
- **Severity**: S2 (Escape-cancel and PTT gestures become unreliable to effectively non-functional under sustained high CPU load; rest of the voice pipeline — wake word, STT, TTS playback itself — keeps working; self-heals once load drops, no restart required)
- **Symptom**: User reported "esc doesnt stop tts anymore." Live `/tmp/heyvox.log` showed the tap health watchdog logging `WARNING: CGEventTap was disabled by macOS, re-enabled (#N)` essentially every 1-2s, continuously, starting 09:26:57 and still ongoing at investigation time (09:34, #386+ and counting; 537 disables in the post-08:36-restart window alone). Cross-referencing `Escape:` log lines showed the mechanism worked 3 times right after an 08:36 restart (08:38:11, 08:43:16, 09:08:31) but zero times since — i.e. Escape presses stopped being captured at all once the flapping became continuous, not merely handled-incorrectly.
- **Root cause**: `start_ptt_listener()` (`heyvox/input/ptt.py`) creates a `CGEventTapCreate` tap and relies entirely on `_tap_watchdog()` — a `time.sleep(1.0)` polling loop — to notice `CGEventTapIsEnabled(tap) == False` and call `CGEventTapEnable(tap, True)`. macOS actually delivers a dedicated notification event (`kCGEventTapDisabledByTimeout` / `kCGEventTapDisabledByUserInput`) to the tap callback itself the instant it disables a tap — Apple's own sample code re-enables synchronously right there — but `_callback_inner()` never checked for these event types, falling through to a bare `return event`. Under system-level CPU contention (observed load average 7.30 on an 8-core machine — consistent with multiple parallel Conductor/Claude agent sessions plus browser renderers, matching [[user_parallel_conductor_sessions]]), macOS was disabling the tap faster than the 1Hz poll could re-enable it, so the effective "listening" window per second shrank to near zero — any Escape press landing in a disabled window was dropped entirely, not mishandled by the `is_busy`/`is_recording`/`is_speaking` branch logic (which is correct and was not the problem — traced `on_cancel_tts` → `_stop_tts_from_escape` → `heyvox.audio.tts.stop_all()` → `heyvox.herald.cli stop` → `_kill_afplay()`+`_clear_tts_state()`+queue purge, all intact).
- **Fix**: Added an immediate in-callback check in `_callback_inner()` (`heyvox/input/ptt.py`) for `Quartz.kCGEventTapDisabledByTimeout` / `Quartz.kCGEventTapDisabledByUserInput` that calls `CGEventTapEnable(tap, True)` and logs, before any other event handling. This doesn't eliminate OS-level starvation under extreme load, but removes the up-to-1000ms self-inflicted lag that made the disabled window compound faster than recovery — the poll-based `_tap_watchdog` remains as a redundant safety net. Restarted via `launchctl kickstart` to apply.
- **Found by**: User's live bug report, root-caused by reading `/tmp/heyvox.log` in real time during the same session (the flapping was actively ongoing at investigation time, not reconstructed after the fact) and cross-referencing timestamps of successful vs. absent `Escape:` log lines against the disable-warning stream.
- **Would have caught earlier**: No test coverage exists for `start_ptt_listener`'s Quartz callback at all — `tests/test_ptt_gesture.py` explicitly scopes itself to the Quartz-free `GestureRecognizer` FSM only ("no real threads or Quartz are involved" by design), and DEF-087/DEF-088 (the original tap-watchdog work) shipped without a mock-Quartz harness either. General pattern: this is the second incident (after DEF-165) where the *symptom* was "CGEventTap flapping," but the two have different root causes (unbounded blocking call vs. missing reactive re-enable) — a synthetic load-test (spin all cores, assert tap re-enable latency stays sub-100ms) would catch both failure classes without needing a full Quartz mock.

## DEF-169 — Garbled-discard recovery pointer (raw WAV → large-v3 reverify) was dead code

- **Date**: 2026-07-02
- **Category**: dead-code / error-handling
- **Severity**: S2 (no crash; the large-v3 reverify-and-clipboard safety net for a discarded transcription silently never ran, for any user, regardless of settings — the discarded text itself is only recoverable by hand from `heyvox-debug/` if debug capture happens to be on)
- **Symptom**: While investigating a user report of "wake word fires, transcription gets thrown away" plus generally slow STT, `/tmp/heyvox.log` + `.log.1` showed 5 `FILTER (garbled, stt=...)` discards in a ~13.5h window, including one on a real, coherent, complete German sentence discarded purely because STT took 11.8s for 14.6s of audio (catastrophic-ratio guard, `text_processing.py`, unrelated to this defect). None of the 5 discards logged "raw audio preserved at ..." or "raw audio captured on-demand for reverify at ..." despite `recording.py` clearly containing that code path, and the HUD showed "Garbled STT - try again" every time instead of "reverifying with large-v3..." — meaning the existing large-v3 background-reverify-and-clipboard-copy feature (`_reverify_garbled_async`) had never actually fired for this user, on a machine where `STT_DEBUG_DIR` was active and the raw/trimmed WAVs for every one of the 5 incidents were confirmed sitting on disk.
- **Root cause**: Two independent, compounding bugs in `heyvox/recording.py`'s local-STT path. (1) `_last_raw_wav` is set inside `stop()` (the method that saves debug audio and dispatches transcription) but read back inside `_send_local` — a *different* method, run on its own daemon thread per its own comment ("_send_local runs on a daemon thread and must not read ctx fields that could be overwritten"). `_last_raw_wav` was never passed as a parameter or stored on `self`/`ctx`, so referencing it in `_send_local` was a guaranteed `NameError` on every single call, silently swallowed by a bare `except NameError: pass`. (2) The on-demand fallback for when debug capture is off (`if _raw_for_reverify is None and audio_chunks: ...` — persists *this* garbled recording to a temp WAV so reverify can still run) checked `audio_chunks` *after* `audio_chunks.clear()` had already emptied that exact list a few lines earlier (`# Free audio chunks immediately — no longer needed after transcription`), so it always saw an empty list and never fired either. Net effect: the recovery/reverify pointer was 100% dead code in every configuration, not just the "debug capture off" case the code comments anticipated.
- **Fix**: Added `raw_wav_path: str | None = None` to `_send_local`'s signature and threaded `_last_raw_wav` through `stop()`'s `threading.Thread(..., kwargs={...})` dispatch so it actually crosses the method/thread boundary. Replaced the `try/except NameError` lookup with a direct `_raw_for_reverify = raw_wav_path` read. Moved `audio_chunks.clear()` from immediately-after-transcription to two call sites — right after the on-demand-fallback save attempt (garbled branch) and right after the garbled-check block (non-garbled branch) — so the fallback can see real audio data in both the "debug capture on" and "debug capture off" cases, while still freeing the buffer at the earliest point each branch no longer needs it (no behavior change for the common non-garbled path). `heyvox/recording.py` only; `text_processing.py`'s ratio-guard itself is untouched — that's a separate, deliberately-not-yet-changed issue (re-tuning it was flagged as the wrong first move; the actual STT-slowness root cause is still open).
- **Found by**: User asked for a log review of a "wake word not ignored + transcription discarded" + "STT is very slow" report. Cross-referencing the 5 `FILTER (garbled)` log lines against `heyvox-debug/` showed the raw/trimmed WAVs existed on disk for every incident even though the log never mentioned them — the discrepancy between "file demonstrably exists" and "code path that's supposed to say so never logs" led directly to the two dead-code sites.
- **Would have caught earlier**: No test exercised `_send_local`'s garbled-discard branch at all (`grep -rl raw_wav_path\|_last_raw_wav tests/` was empty before this fix) — the NameError-swallow and the clear()-ordering bug both hide in exactly the kind of place only an explicit test looks: a rare (garbled), silently-caught-exception (bare `except: pass`) branch. Added `test_stop_passes_raw_wav_path_kwarg_to_send_local`, `test_send_local_garbled_with_debug_wav_triggers_reverify`, and `test_send_local_garbled_without_debug_wav_falls_back_on_demand` to `tests/test_recording_state.py`; confirmed all three fail against the pre-fix code (via `git stash`) before confirming they pass against the fix. General pattern, adjacent to P-log-path-split below: a bare `except SomeSpecificError: pass` around a variable *reference* (not a fallible operation) is almost always masking a scoping bug, not handling a real runtime condition — worth a second look wherever this shape appears.

## DEF-170 — STT-slowness system-contention root cause had no automatic log signal (process gap, not a crash)

- **Date**: 2026-07-02
- **Category**: dead-code / config (observability gap)
- **Severity**: S3 (no functional impact; closes a process gap that made a real user-facing symptom — slow STT — expensive to root-cause)
- **Symptom**: Following the DEF-169 investigation, the user asked to tackle the still-open item: *why* STT decode occasionally takes 10-20x its own warm baseline (5 of 40 sampled completions in the prior investigation exceeded 10s, two exceeded 20s, `warm=True` in every case — not a cold-reload story). The prior investigation could only correlate this with system memory pressure *after the fact*, by manually cross-referencing `[RAM_PRESSURE]` log lines against STT timing lines, and even then only explained one of two slow-STT clusters — the other showed moderate RAM (2100-2700MB) with no obvious excuse.
- **Root cause**: No log line captured system contention *at the moment* of a slow STT completion — `heyvox/ram_pressure.py` already existed and periodically banners on RAM pressure, but (a) it polls independently on its own ~60s cadence, not synchronized with individual STT calls, and (b) it only measures RAM, not CPU. Checking the live machine mid-investigation (`uptime`, `ps aux -r`) found load averages of 13.82 and later 32.2 on an 8-core M1 Pro, with 4+ concurrent `claude` agent processes plus Conductor's own WebKit/WindowServer overhead visible in `ps` — consistent with [[user_parallel_conductor_sessions]] (Franz routinely runs 3-5 parallel Conductor/Claude sessions) and the same load-average-oversubscription class already named in DEF-168 (CGEventTap starvation, load avg 7.30 that time). RAM pressure alone does not capture this: at the moment of the `load1=32.2` reading in this session, `avail_mb=7946` and `pressure=normal` — i.e. the machine was clearly CPU-oversubscribed while looking completely healthy on the RAM-only signal. This is very likely the same underlying mechanism as the STT slowness (MLX Whisper inference competing for CPU/GPU scheduling and unified-memory bandwidth against other heavy processes), but is now a strongly-supported live-evidence correlation, not a proven per-historical-incident causation.
- **Fix**: Added `heyvox.ram_pressure.contention_snapshot()` — a small, defensive (never-raises, each field independently degrades to `"?"`) function returning `avail_mb=N pressure=<normal|warn|critical|?> load1=N` — and wired it into the existing `[TIMING] stop→STT done` log line in `heyvox/recording.py` so every single STT completion (not just slow ones) now carries a synchronized system-contention snapshot. This is instrumentation only: it does not change STT behavior, does not touch the `is_garbled` ratio threshold, and does not attempt to mitigate the contention (e.g. thread priority, adaptive model fallback) — those remain open, deliberately deferred pending more data from this signal and a separate discussion, since the two obvious levers (re-tuning a ratio guard that's already been tuned once; asking Franz to run fewer parallel sessions) both have real downsides raised in the prior investigation.
- **Found by**: Live system inspection (`uptime`, `ps aux -r`, `memory_pressure`) during this session, cross-checked against the already-existing but RAM-only `heyvox/ram_pressure.py` module and its docstring (which documents cold-reload latency from RAM pressure, a *different and less severe* symptom than the warm-inference 10-20x slowdown actually observed).
- **Would have caught earlier**: This entry *is* the "would have caught earlier" for the DEF-169 investigation — the STT timing log now carries the context needed to confirm or rule out system contention on sight, for every future slow-STT report, without re-deriving it by hand. General pattern: a periodic/independent monitor (ram_pressure's 60s poll) is not a substitute for a synchronized snapshot at the exact moment of the event you're trying to explain — the two serve different purposes (background banner vs. point-in-time correlation) and this codebase only had the former for STT latency investigations.

## DEF-171 — MLX/sherpa transcription worker thread ran at default QoS despite the machine being routinely CPU-oversubscribed

- **Date**: 2026-07-02
- **Category**: timing / platform
- **Severity**: S3 (experimental mitigation for the DEF-169/DEF-170 slow-STT investigation, not a confirmed fix — explicitly shipped without automated test coverage or live A/B verification at the user's request)
- **Symptom**: Continuation of the same-day STT-slowness investigation (DEF-169, DEF-170). With `contention_snapshot()` now live, this session confirmed load averages of 13.82 and 32.2 on an 8-core M1 Pro at moments unrelated to any single STT call — i.e. the machine is routinely oversubscribed by parallel Conductor/Claude sessions, not just during rare spikes.
- **Root cause**: `transcribe_audio()`'s `ThreadPoolExecutor` worker (`heyvox/audio/stt.py`, both the MLX and sherpa branches) ran `mlx_whisper.transcribe(...)` / the sherpa decode loop at whatever QoS class Python's default `threading.Thread` gets — no different from any other background thread on the machine, competing on equal footing with WebKit renderers, other `claude` processes, etc. for the same 8 cores. - **Found by**: Direct continuation of the DEF-170 investigation at the user's explicit instruction to try the thread-priority lever.
- **Would have caught earlier**: N/A — this is a same-session experimental change, not a regression. **Follow-up needed**: `contention_snapshot()` (DEF-170) now rides on every STT log line specifically so this can be evaluated with real data — watch for (a) whether `load1`-correlated STT slow-tail outliers shrink after this ships, and (b) any recurrence of DEF-168-style `CGEventTap was disabled` flapping correlated with active transcription, which would mean `USER_INITIATED` still contends too much and the PTT thread needs its own explicit QoS floor rather than relying on relative default-vs-boosted weighting.

## DEF-172 — Cue playback (listening/ok) silently routed to the wrong output device while TTS routed correctly

- **Date**: 2026-07-03
- **Category**: platform / error-handling
- **Severity**: S2 (audible feedback cues effectively inaudible to a headset-wearing user — they play, just not where the user can hear them; voice input, wake word, and TTS speech all keep working correctly)
- **Symptom**: User reported that "listening"/"ok" cues played through the MacBook's internal speaker while TTS speech played correctly through the G435 headset, at the same time, both macOS System Settings and HeyVox's own reported output device showing the headset as active. This followed a separate incident earlier the same day where the G435's USB/Lightspeed dongle flickered for several minutes (confirmed via `coreaudiod`'s own `AudioAnalytics` telemetry showing repeated `output_device_source_list: Internal Speaker` and the USB audio engine's `IOWorkLoopInit`/`IOWorkLoopDeinit` cycling every few seconds), which independently caused a total mic outage (cooldown-storm on all input devices, fixed by a daemon restart) and a transient TTS misroute (self-resolved once the flapping stopped, since `afplay` re-resolves fresh per call).
- **Root cause**: `OutputKeepAlive._open_stream()` (`heyvox/audio/keepalive.py`) opened its PyAudio output stream via `pa.open(output=True, ...)` with no `output_device_index` — relying entirely on PortAudio's own internal default-output resolution rather than the live CoreAudio default that `default_output_transport()` (same file, two lines earlier) had just verified via direct ctypes. `cues.py`'s `_play_via_sounddevice()` fallback had the identical gap: `sounddevice.play(data, samplerate)` with no `device=`. Both mechanisms can silently diverge from the live CoreAudio default after device churn — confirmed empirically: a brand-new process's PyAudio default resolved correctly to the G435 at investigation time, but the *already-open* keep-alive stream (opened once, hours earlier) had no mechanism to notice if the underlying device object had since been swapped by a reconnect that didn't change the transport type (USB → USB), since the monitor loop (`_loop()`, 5s poll) only reacts to *transport-type* flips, not same-transport object churn. Once such a stream opens "successfully" against a stale-but-still-valid device, `play_cue()` only checks `self._stream is not None` — no exception is ever thrown, so DEF-153's failure-triggered context-drop-and-recreate never fires. This is a distinct failure mode from DEF-104/148/150/153 (which all recover from *loud* failures) — here nothing fails, it's just silently bound to the wrong device. TTS never hits this class of bug at all: `orchestrator.py` spawns a fresh `afplay` OS process per utterance, which re-resolves CoreAudio's live default every single time, immune to any process-lifetime caching.
- **Fix**: Added `get_default_output_name()` to `heyvox/audio/output.py` (thin wrapper over the module's existing, already-correct `get_default_output_id()` + `_get_device_name()`). `keepalive.py`'s `_open_stream()` now resolves the matching PyAudio device index (by name + `maxOutputChannels > 0`, to disambiguate the G435's separate input/output sub-devices which share one name) via a new `_resolve_output_index()` and passes it explicitly as `output_device_index=`; it also now re-resolves on *every* monitor tick (not just on open) and recycles the stream (close + reopen against the new index) if the target index changed while `self._stream` was already set — closing the same-transport silent-churn gap, not just the open-time binding. `cues.py`'s `_play_via_sounddevice()` gained the equivalent `_resolve_sounddevice_output_index()` matching against `sounddevice.query_devices()`. Both resolvers degrade to `None` on any failure (missing method, device vanished mid-lookup, etc.), which both `pyaudio.Stream.__init__` and `sounddevice.play()` document as behaving identically to omitting the parameter (verified against the installed packages' own docstrings, not assumed) — so today's original behavior is the fallback, never a hard failure. Also improved the `[keepalive]` open-success log line to record the resolved `device_index=`, closing a diagnostic gap that made this incident require live `coreaudiod` unified-log forensics to root-cause instead of a one-line log read.
- **Found by**: User's live report during the same session as the G435 flicker investigation, immediately after being told the flicker was already resolved — the cue/TTS device split was still actively reproducing at report time (unlike the earlier transient misroute), which is what made it root-causeable rather than another one-off.
- **Would have caught earlier**: No test asserted that cue playback and TTS playback resolve to the *same* output device — `test_def148_keepalive_opens_one_stream_and_closes` and `test_def153_...` both stub `FakePA.open(**kw)` without ever inspecting *which* device index was requested, so a missing/wrong `output_device_index` would pass silently. General pattern (ties into P-silent-wrong-device below): any fix that recovers from a *failure* needs a companion check for the *silent-wrong-result* variant of the same bug, because "no exception" is not the same as "correct."

## DEF-176 — Hush native host opened an unauthenticated TCP port (127.0.0.1:9847) allowing local text+Enter injection into the focused browser tab

- **Date**: 2026-07-03
- **Category**: dead-code / security
- **Severity**: S1 (security) — rated HIGH / pre-launch blocker by the security audit; a working "inject arbitrary text and submit it with Enter into whatever the victim's browser currently has focused" primitive (password fields, web terminals, email compose), reachable by any co-resident local process or a different OS user on a shared Mac. The Unix socket (0600, inside 0700 `$TMPDIR`) remains the sole IPC channel. Chose removal over a shared-secret token because the channel had zero consumers — deleting the door is strictly better than guarding a door nobody uses. Verified no client, doc, JS, or test referenced the port before removal (grep across `*.py`/`*.sh`/`*.js`/`*.md`).

General pattern: any IPC "fallback" transport needs an actual consumer or it should be deleted, and any listener that cannot inherit the `$TMPDIR` 0700 per-user isolation (a TCP port, by definition) is a defense-in-depth regression that must be flagged at review — see the P-network-listener-bypasses-tmpdir pattern below.

## DEF-177 — Lua string-breakout in Herald orchestrator: workspace label / alert message could inject into `hs -c`

- **Date**: 2026-07-03
- **Category**: string-handling / security
- **Severity**: S2 — an external → local-code-execution chain, but narrow preconditions (Hammerspoon installed and running, hold-queue enabled, and a crafted value reaching the label). Bounded to `hs -c` (Lua) execution as the local user; not remotely reachable.
- **Symptom**: A workspace label containing a backslash immediately before a single quote (e.g. `foo\' .. os.execute('touch /tmp/pwned') .. '`) was not neutralized before being interpolated into the single-quoted Lua string that `_notify_held()` runs via `hs -c`. The crafted `\'` unbalanced the Lua string literal, so trailing tokens ran as Lua rather than being treated as label text.
- **Root cause**: `_notify_held()` escaped the label with `workspace.replace("'", "\\'")` — it escaped the single quote but not the backslash. Since a lone `'` becomes `\'` while a preceding backslash is left untouched, an attacker-supplied `\'` composes into `\\'` in the wrong way: the backslash escapes itself and the quote ends up bare, terminating the string. Escape order must be backslash-first (`\` → `\\`) then quote (`'` → `\'`), the order already used correctly for AppleScript in `injection.py`/`toast.py`. The tainted `workspace` value flows from `get_workspace_label()`, whose precedence includes a Conductor **PR title** pulled from Conductor's SQLite DB — an externally-authored string on any public repo the user opens a workspace against. The sibling `_show_alert()` (herald/orchestrator.py) did **zero** escaping of its `message` arg — safe only because today's callers pass int-formatted strings (`f"{len(remaining)} more pending"`), but the same injection class the instant any caller passes user text.
- **Fix**: Added a module-level `_lua_str_escape()` helper in `heyvox/herald/orchestrator.py` — escapes backslash first, then single quote, then neutralizes raw CR/LF (which would otherwise terminate a single-quoted Lua string). Routed both `_notify_held()` (workspace label) and `_show_alert()` (message) through it. `_show_alert` is escaped pre-emptively despite its currently-safe callers, closing the latent path rather than relying on caller discipline.
- **Found by**: Launch-readiness security audit (2026-07-02), `.context/release-audit/03-security.md` §1 — reproduced the `\'` breakout against a local Lua interpreter.
- **Would have caught earlier**: No test exercised the Lua-escaping of either call site (the AppleScript escaping in `injection.py` was tested; the Lua path was not). Added `tests/test_herald_lua_injection.py` — an adversarial round-trip that decodes the escaped output as a Lua single-quoted string and fails on any bare quote / dangling backslash (proving no breakout), plus behavioral coverage that both `_notify_held` and `_show_alert` embed only the escaped form in the `hs -c` argv. General pattern: whenever a value is interpolated into a *different* language's string literal (Lua, AppleScript, SQL, shell), the escaping must match that target language's actual rules and be applied in the composition-safe order (escape the escape character first) — and every such site needs a breakout test, not just the first one written.

## DEF-178 — MCP shared-HTTP server has no per-user auth; loopback bind was the only thing protecting the TTS-control tools (documented + regression-guarded)

- **Date**: 2026-07-03
- **Category**: security / config
- **Severity**: S3 — bounded blast radius (TTS control only: `voice_speak`/`voice_queue`/`voice_config`; no filesystem/subprocess/credential tool exposed), opt-in transport, and the default install has no port at all. - **Found by**: Launch-readiness security audit (2026-07-02), `.context/release-audit/03-security.md` §3b (verified live: bind is `127.0.0.1`, forged Origin → 403, no-Origin curl → 200).
- **Would have caught earlier**: Nothing would surface this as a runtime symptom (it's a design gap, not a crash). Added `tests/test_mcp_server_security.py` (net-free): `_is_loopback_host` accepts only loopback forms and rejects routable addresses; the `--host` default stays `127.0.0.1`; the non-loopback warning branch and the no-auth disclosure stay in source. General pattern: when a security property is enforced *implicitly* by a default (here, "loopback bind ⇒ Origin protection + no LAN exposure"), add a test that pins the default and a runtime guard that warns when it is overridden — implicit protections silently disappear under a one-line config change.

## DEF-180 — CI had no secret-scanning or dependency-CVE gate

- **Date**: 2026-07-03
- **Category**: config (CI process gap)
- **Severity**: S3 — no active vulnerability; a missing recurring gate. Its absence is exactly what let one-time audits substitute for continuous scanning.
- **Symptom**: All three workflows (`ci.yml`, `install-test.yml`, `publish.yml`) ran functional tests + ruff + actionlint only — no `gitleaks`/`trufflehog` secret scan and no `pip-audit`/`safety` dependency-CVE check. A secret committed in a future push, or a newly-disclosed CVE in a transitive dependency, would go unflagged.
- **Root cause**: Never added; the audits doing secret/dep scanning were manual, point-in-time passes, not a repeatable CI gate.
- **Fix**: Added a `security` job to `ci.yml` (ubuntu-latest): (1) **gitleaks** secret scan — version-pinned to 8.30.1 **and sha256-checksum-verified** (supply-chain hygiene for the scanner binary itself), run as `gitleaks dir .`; **blocking**, since a leaked credential is always author-actionable. (2) **pip-audit** dependency-CVE audit — **non-blocking** (`continue-on-error`), because heyvox transitives (starlette via FastMCP, urllib3, requests) periodically carry CVEs that need an upstream release, and a hard gate would red CI on issues the maintainer can't immediately fix; it runs on every push for visibility and can be promoted to blocking once the tree is clean. Added `.gitleaks.toml` extending the default ruleset with one allowlist entry: the Hush Chrome-extension `manifest.json` embedded **public** key (base64 RSA SubjectPublicKeyInfo), which gitleaks' `generic-api-key` rule flags on entropy — a genuine false positive (the key is public by design, pins the extension ID, ships in every browser).
- **Found by**: Launch-readiness audit §4 (secrets) + §7 (supply chain), both recommending these as the ongoing repeatable gate.
- **Would have caught earlier**: This *is* the caught-earlier mechanism. Notably, standing up the gitleaks gate immediately surfaced one finding the earlier keyword/pickaxe history scan had not (the extension public key) — validating that the broader-ruleset scanner earns its place even though that specific hit was a false positive. General pattern: replace one-time manual security passes with a pinned, checksum-verified CI gate; block on author-actionable classes (secrets), report-only on externally-gated classes (transitive CVEs) until the baseline is clean.

## Patterns & Process Gaps

- **P-silent-wrong-device** (DEF-172, sibling to DEF-104/148/150/153): a long-lived PortAudio (pyaudio/sounddevice) stream or context can remain "open" and functionally healthy while bound to a device object that CoreAudio has since superseded, if the underlying device swap doesn't cross a boundary the code actually watches (e.g. transport type staying USB→USB across a reconnect). Unlike DEF-104/153's failure mode (loud errors: `-9986`/`-10851`), this variant throws nothing — recovery logic gated on exceptions (`stale` counters, drop-and-recreate-on-failure) never fires. **Action item**: any code opening a PortAudio-family stream against "the default device" should (a) resolve and pass an explicit device index/UID rather than relying on the library's own default resolution, matching it against a live CoreAudio query, and (b) re-validate that binding periodically, not just at open time — "open succeeded" and "bound to the right device" are different claims and only the fix for DEF-172 checks both.
- **P-log-path-split** (DEF-126, recurred as DEF-166): any module that logs independently of the central `main.py` `log()` risks silently diverging from "the log everyone tails." DEF-126 was a wrong-*path* variant (module read a different config field/default than main.py). DEF-166 is a wrong-*transport* variant (module wrote via stderr/fd instead of reopening by path), which is more dangerous because it works fine until the first rotation, then goes silent for the rest of the process's life with no error. **Action item**: any new module-level `_log()` must reopen the resolved log path per call (copy `_resolve_log_path()` from `injection.py`/`target.py`), never `print(file=sys.stderr)` — even though launchd also redirects stderr to the same path at startup, that redirect does not survive `main.py`'s rename-based rotation. `mic.py`, `ptt.py`, `toast.py`, `adapters/conductor.py` still need this fix; audit before the next release.
- **P-unbounded-native-call**: `subprocess.run(..., timeout=...)` is used consistently in this codebase, but PyObjC/AppKit calls (NSPasteboard, NSWorkspace, and likely others) were never given the same scrutiny because they're normally sub-millisecond — until the underlying system service (pasteboard server, WindowServer) itself stalls, at which point they block forever with no recourse. **Action item**: any new PyObjC call added to a single-threaded event-loop path (main.py, recording.py, injection.py, target.py) should go through `_call_with_timeout()` (`heyvox/input/injection.py`) rather than being called directly.
- **P-retroactive-labeling** (DEF-167): any training/label-correction mechanism which infers a label from OUTCOME OR TIMING rather than re-examining the underlying evidence (audio transcript, in this case) risks manufacturing exactly the class of error it claims to fix. **Action item**: any future auto-labeling code path in this training pipeline must be evidence-based (derive the label from re-inspecting the actual data, e.g. via STT) or must run through the same mandatory `tools/quality_gate.py` chokepoint before its output is trusted.
- **P-network-listener-bypasses-tmpdir** (DEF-176, sibling to the Chrome WebSocket bridge `:9285` cut in the Phase-1 install work): the codebase's IPC security model rests on the per-user `$TMPDIR` 0700 directory plus 0600 socket files — a strong mitigation that applies only to filesystem-backed channels (Unix sockets, flag files). Any TCP/WebSocket listener silently opts out of that model: a port cannot be `chmod`'d and is reachable by any co-resident process or (for TCP) any local user account. Both network listeners found in the audit (`hush_host.py` TCP `:9847`, `chrome/bridge.py` WebSocket `:9285`) were alternate transports that had been superseded by the Unix-socket design but never removed, and both lacked auth/Origin protection. **Action item**: prefer `AF_UNIX` for all local IPC. If a TCP/WebSocket listener is genuinely required, it must (a) bind `127.0.0.1` only, (b) authenticate (shared-secret token from a 0600 file, or Origin/Host validation for HTTP), and (c) have at least one real consumer — otherwise delete it. Add a listener-surface guard test whenever such a channel is introduced (see `tests/test_hush_host_security.py`).
